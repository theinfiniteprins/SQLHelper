Internal R&D — Feasibility Report

Running one fix across thirty identical client databases

Between the bi-monthly releases, every out-of-band fix — a data correction, an altered stored procedure — is applied by hand in SSMS, database by database. This report assesses a local-only tool that fans one statement out to a chosen set of client databases, and reports which parts are achievable, which carry caveats, and which are not.

2026-09-04 Scope: 30+ databases · identical schema · SQL Server Status: research, no build

Bottom line

Effectively all of it is achievable, and the hardest requirement is the safest to build

Nothing in the request needs technology that does not already exist as a documented, offline-capable library. The programmable-object workflow — capture the current definition, file it, then run the ALTER — is not only feasible, it is the cleanest piece to build well, because module DDL in SQL Server is transactional and every "before" state is a plain text definition you can read with one query.

The harder refinement you raised later — changing a few lines inside each client's own copy of a procedure when those copies have drifted apart — is also buildable. It works by clustering the clients into their handful of distinct versions and patching against an anchor in the text rather than replacing the file. That is its own section below.

Feature feasibility

Screen by screen

1 · Database registry

✓ Achievable

An editable grid (one row per database: server, database name, login, password, plus an environment tag and a free-text client name). Support pasting a block straight from Excel — the clipboard delivers it as tab-separated text — and importing a .xlsx with ClosedXML, which needs no Office install. The list is saved to one encrypted file under %APPDATA%, never beside the executable and never in source control.

Add named target groups here ("All production", "EU clients", "Pilot") so later screens select a group instead of ticking boxes each time.

2 · SELECT runner

✓ Achievable

Read-only is enforced in depth, because no text check alone is trustworthy:

  • Parse, don't regex. Microsoft.SqlServer.TransactSql.ScriptDom is Microsoft's own T-SQL parser. Walk the syntax tree and reject anything that is not a SELECT — it catches EXEC, UPDATE … OUTPUT, and a CTE that ends in INSERT, all of which a keyword filter misses.
  • Wrap every run in a transaction that is always rolled back.
  • Best of all, give this screen a login that only holds db_datareader. Enforced by the server, nothing to trust in the client.

Queries fan out in parallel with a small concurrency cap (SemaphoreSlim, 4–8 at once), each with its own timeout and a global cancel. Results show as one grid per client plus a combined grid with a leading Client column; export writes an .xlsx with either a sheet per client or one stacked sheet.

3 · Update / Delete runner

△ Achievable, with caveats

Row counts per database come straight from @@ROWCOUNT / ExecuteNonQuery. The important addition is a dry run: execute inside a transaction, capture the count, ROLLBACK, and show "would affect N rows" for every target before anything commits. Then run for real, each database in its own transaction, with a "stop on first error" / "continue" choice and a re-run failed only action afterwards.

Guardrails worth making mandatory: a warning when an UPDATE/DELETE has no WHERE; a confirmation when the row count crosses a threshold; a typed confirmation for anything tagged production; and a required change title or ticket reference recorded with every write.

4 · Programmable-object deployment

✓ Achievable

Stored procedures, table-valued and scalar functions, views, triggers. This is the special requirement and it gets its own section below.

The "nothing leaves the machine" requirement

What local-only actually means, and how to prove it

Credentials at rest

  • Best case — store no passwords at all. Where the SQL Servers are reachable through domain trust, use Windows Authentication (Integrated Security=true). The registry then holds no secrets.
  • Otherwise — DPAPI. ProtectedData.Protect(…, DataProtectionScope.CurrentUser) encrypts each password with a key derived from the Windows account on that machine. The ciphertext is useless copied to another user or another PC, and there is no key file to manage.
  • Optional master password on launch: derive entropy with Argon2id and pass it to DPAPI as optionalEntropy, so the store cannot be read even by the same Windows user without the passphrase.
  • Connections use Encrypt=True so traffic to SQL Server is TLS-protected; install proper server certificates rather than setting TrustServerCertificate=True.

No egress

The application makes no outbound connection except to the registered SQL Servers on their configured port. No telemetry, no auto-update check, no crash reporting, no licence activation. This is verifiable, not just asserted:

  • Ship a single self-contained, code-signed executable so IT can allowlist it.
  • A host firewall rule that permits only TCP 1433 to the known server subnet will not interfere with the tool — and will block anything else it might try.
  • Pin and review every NuGet dependency version; build offline if policy requires it.

Deep dive

The programmable-object engine

For each selected database, and each target object, the tool runs five steps:

  • Read the current definition — OBJECT_DEFINITION(OBJECT_ID(N'dbo.usp_GetOrders')) or sys.sql_modules. For a richer script (SET options, permissions), SMO's Scripter.
  • Write the backup file before touching anything (layout below). An object that does not yet exist gets a marker file recording that it was new.
  • Execute the change. Prefer CREATE OR ALTER (SQL Server 2016 SP1+). Split the script on GO first — GO is an SSMS convention that ADO.NET does not understand; ScriptDom or SMO handles the batching. Module DDL is transactional, so wrap it and roll back on error.
  • Verify — re-read the definition and record its checksum.
  • Log the result to the audit trail.

Each file opens with a header comment: server, database, object, capture time, checksum, tool version, operator.

Because the "before" state is captured, four things come almost for free
  • One-click rollback. The captured definitions are the revert script; generate and keep it per database.
  • Pre-flight diff. Show current-vs-new per database before running — this is how you catch a client that has a hand-customised version of the procedure before you overwrite it.
  • Drift report. Hash each target object across all 30 databases and flag the ones that differ from a chosen reference. Answers "is every client actually on the same code?"
  • Skip-if-identical. If a database already has the new definition, log "already current" and move on.

Point the backup folder at a local Git repository and auto-commit each run: full history, diff and blame, still entirely on the machine.

Deep dive — the harder case

Changing a few lines when every client's copy is different

A blanket "deploy this definition everywhere" is wrong once clients have drifted. One client's procedure may take different parameters or carry extra logic, so overwriting it with the canonical version breaks that client's callers or throws on deploy. What you want instead is to change the same 2–3 lines inside whatever each client currently has, and leave the rest of their copy alone.

The insight that makes it manageable

Clients do not drift into 30 unique versions — they cluster into a handful. The tool hashes the normalised definition of the target object across every selected client and groups them, then reports something like: "24 clients on canonical, 4 on variant B, 2 on variant C." You author the change once per variant, not once per client. The worst case is the number of distinct versions, not the number of clients.

A progressive apply strategy

The change is stored as a patch — an anchor plus a replacement — never as a whole file. For each client it is tried in tiers, stopping at the first that succeeds:

Tier 1 · exact Anchored replaceThe old lines plus auto-expanded surrounding context, matched with whitespace normalised. Found exactly once in the procedure → replace.
Tier 2 · fuzzy Tolerant matchIf the exact anchor fails, match with tolerance for shifted or lightly edited context (diff-match-patch patch_apply). Applied, but flagged with its offset for a human to eyeball.
Tier 3 · manual Focused merge editorIf the target region itself is customised, the tool opens a two-pane editor for that one client with your intended change highlighted. You make the edit by hand; the tool records "Client X handled manually for change ORD-1487".

Every tier ends the same way: re-parse the result with ScriptDom and reject anything that is not valid T-SQL; check the change size is sane (a 3-line patch that produces 40 changed lines is aborted); and show the resulting unified diff for approval.

Pre-flight — your "it throws an error" concern

Before any patch, build a signature for the target object on every client from sys.parameters: parameter names, types, order, defaults, output flags — and result shape for table-valued functions. Compare each client to canonical and flag every one whose signature differs. Those are exactly the clients where a wrong move breaks callers, and the ones most likely to fall to Tier 3. This runs as a gate — you see it before committing to anything.

Per-client dry run, then the normal pipeline

A grid before anything is written: client · current variant · apply tier · resulting diff · signature match · approve. Approve the clean cohort in bulk; handle or defer the flagged clients one at a time. Once approved, it is the same pipeline as an ordinary deploy — back up each client's actual current definition, apply, re-fetch and confirm the patched lines are present, and generate a per-client rollback from the captured original.

What still needs a human
  • A client whose target region has genuinely been rewritten needs a manual edit. The tool narrows the work to that one client and that one region, but it cannot guess intent.
  • Fuzzy matching can place a change in the wrong spot if the anchor is not unique — mitigated by forcing the anchor to be unique within the procedure (auto-expand context, or else require Tier 3) and by mandatory diff review.
  • If someone is mid-way through their own uncommitted customisation of a client, you will see it as drift with no clean anchor. Correct behaviour — but it means coordinating with whoever owns that client's code.

Building blocks

  • diff-match-patch (C# port) — fuzzy patch application with per-hunk success/failure reporting. The workhorse for Tier 2.
  • ScriptDom — validate every patched result; also parse-and-re-emit to produce a normalised form for drift hashing, so whitespace and comments do not register as separate variants.
  • DiffPlex (.NET) — side-by-side diffs for the review screens.
  • sys.parameters / sys.sql_modules — profiling and signature extraction.
  • git merge-file (ships with Git) — optional true three-way merge, if you keep canonical definitions in version control and therefore have the common ancestor.

Hard limits

What the tool cannot do, however it is built

Set expectations here
  • No single atomic transaction across all 30 servers. That needs distributed transactions (MSDTC) and is fragile at this scale. The honest model is per-database transactions plus the auto-generated rollback scripts plus "re-run failed".
  • "Is this query read-only?" cannot be proven from text alone — mitigated, not eliminated, by the syntax-tree check plus a reader-only login.
  • No point-in-time data recovery after a bad UPDATE. That is what SQL Server's native backups are for; the tool can only snapshot the affected rows to a file beforehand.
  • Table and column drift between clients is detectable but outside the stated scope — a natural later feature.
  • A determined insider is not stopped by a local tool; the audit trail narrows the risk, it does not remove it.

Recommendation

Stack, and whether to build at all

If built in-house

C# / .NET 8 with a WPF (or WinForms) front end. Microsoft.Data.SqlClient for execution, Microsoft.SqlServer.TransactSql.ScriptDom for parsing and GO-splitting, SMO for scripting object definitions, ClosedXML for Excel, ProtectedData for the credential store, and an append-only audit log (SQLite or JSONL: operator, time, targets, full statement, counts, checksums, duration).

Before writing SQL plumbing, look at these

  • dbatools — free, open-source PowerShell. Invoke-DbaQuery, Get-DbaModule and Export-DbaScript already do multi-instance execution and object scripting. The fastest safe way to build the engine; a thin UI can wrap it.
  • DbUp / Flyway — local migration-script runners with per-database version tracking. They solve "run this everywhere, once, in order" but not the ad-hoc SELECT/export or the auto-scripting of the old procedure.
  • Redgate SQL Multi Script — commercial; does the multi-database query and export today, but not the backup-then-alter workflow, and is third-party code to vet.
Structural option worth weighing

The root problem is out-of-band change. If every fix — data corrections included — became a numbered migration script in source control, applied by a runner that tracks a SchemaVersions row per database, then "did I run this on client 17?" stops being a question. The tool then mainly needs target selection, a "show pending / apply" screen, and the SELECT utility — with your bespoke backup step layered on the object migrations.

Verdict: the specific combination — ad-hoc client-wise SELECT with export and the auto-backup deployment engine — is niche enough to justify a small internal tool. Build its core on dbatools or the Microsoft libraries; do not hand-roll the SQL internals.

Roadmap

Suggested build order

Roughly one developer. Each phase is independently useful on the day it ships.

PHASE 1

Registry + SELECT runner

Grid entry, paste-from-Excel, DPAPI store. Parallel SELECT, client-wise grid, Excel export, syntax-tree read-only guard. ~2–3 weeks

PHASE 2

Update / Delete runner

Dry-run row counts, per-DB transactions, audit log, target groups, production confirmation, re-run failed. ~2 weeks

PHASE 3

Programmable-object engine

Auto-backup folder, GO handling, CREATE OR ALTER, manifest, auto-generated rollback, local Git versioning. ~3–4 weeks

PHASE 4

Fleet visibility

Cross-client drift & cohort grouping, pre-flight signature check, transient-error retry, affected-row snapshots. ~2 weeks

PHASE 5

Targeted patch mode

Anchor / fuzzy / manual apply pipeline, per-client dry-run grid, ScriptDom validation, per-client rollback from the captured original. ~3 weeks

A solid Phase 3 lands in roughly two months — one release cycle — with Phases 1 and 2 in use well before that. Phases 4–5 turn it from a deployment tool into a way to manage the whole client fleet.
